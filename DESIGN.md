# Design rationale

Release 1 uses simple dictionaries for a stable six-field transaction contract instead of introducing a class hierarchy. The CLI gathers input and displays results, while the service layer implements transaction operations and reporting without user prompts or file operations. Validation is centralized at the two entry boundaries—adding a transaction and importing CSV—so invalid IDs, dates, categories, currencies, and amounts are rejected consistently with actionable error messages. The storage layer validates complete CSV input before returning it to the CLI, preventing partially imported data from replacing the current list. Reports remain separated by currency because adding EUR to USD without an exchange rate would misrepresent the business balance. This modest modular design keeps individual behaviors testable and makes future improvements possible without rewriting the entire application.
